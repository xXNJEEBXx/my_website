# المراجعة الثانية — 27 أكتوبر 2026

## النتيجة

المراجعة الأولى أصلحت عيوب التنفيذ، لكنها بالغت في جعل التعلم والتحديث يدويين. أُعيد ربط التطوير التلقائي بجمع الأدلة والتعلم، مع الحفاظ على عزل البيانات. هذه مراجعة للإضافة وتعليمات التقديم المرتبطة بها، وليست تدقيقًا كاملًا لمنظومة التليجرام والتراكر.

## التحديث التلقائي

كان موجودًا سابقًا: watcher يعيد تحميل الإضافة والتبويب النشط. أُوقف في دفعة 26 أكتوبر، ثم استُعيد في هذه الدفعة وفق المسار التالي:

1. `npm --prefix cv-autofill-extension run dev` ينشئ إعداد تطوير محليًا محميًا ومُستبعدًا من Git.
2. بعد تحميل نسخة الإضافة الحالية، اضغط فحص لتتصل بوضع التطوير. بعد تعديل manifest يلزم تحديث Chrome المعتاد مرة أولى.
3. تعديل المصدر يشغّل build وفحص صياغة جميع مصادر JavaScript. عند الفشل لا تُنشر إشارة تحديث.
4. رقم مراجعة محفوظ يمنع ضياع التغيير عند انقطاع الاتصال أو إعادة تشغيل العامل.
5. التحديث ينتظر إذا كان التنفيذ جاريًا أو كان نموذج مرتبط يحتوي بيانات غير مرسلة. عند خلوه تُحدّث الإضافة والنماذج المرتبطة فقط، مع مطابقة URL قبل تحديث التبويب.
6. لا يُعاد تحميل تبويب غير متعلق لمجرد أنه نشط. إيقاف خادم dev يعطل المسار.

أثبت اختبار Chrome الفعلي أن النموذج المعبأ يبقى دون فقد بيانات، ثم تتم إعادة تحميل الإضافة والنموذج نفسه بعد تفريغه. كشف الاختبار أيضًا ضرورة تفعيل Developer Mode كما يشترط تثبيت unpacked؛ التحميل عبر CDP وحده لم يكن يحاكي هذه الخطوة.

## التحسن مع التشغيل

أصبح هناك تمييز بين ثلاثة أشياء:

- **ذاكرة التشغيل:** آخر 100 نتيجة، بما فيها عدادات الحقول وأكواد الفشل والفجوات المنظفة ومدة التشغيل، داخل تخزين الإضافة.
- **تعلم الربط:** الحقول التي نجحت بقاعدة منصة موثوقة تُحفظ كمفاتيح للسيرة. تصحيح المستخدم المعتمد له الأولوية، ولا يتجمد الاسم أو الهاتف كنص قديم عند تحديث الملف. يعتمد التعرف على التسمية وإطار السؤال بدل معرّف مولّد وحده.
- **تحسين الكود:** الوكيل يحول الفجوة إلى حالة قابلة للإعادة، ويعدل الطبقة المسؤولة، ويشغل اختبارات الإنتاج قبل اعتماد التعميم. runtime لا يكتب كودًا جديدًا بنفسه.

تُلتقط عينات منظفة تلقائيًا عند تفعيل dev، وتُحفظ دون تكرار. لا تُرسل العينات خارج الجهاز، ولا تُخزن قيم الحقول في سجل التشغيل. عمليات حفظ القواعد تمر عبر طابور واحد لمنع فقد قواعد عند عمل إطارات متعددة. الربط التلقائي لا يستبدل قاعدة صريحة، ولا تُخترع إجابة لسؤال مجهول.

## التعليمات والتكرار

لم يكن التكرار محصورًا في README وagent-learnings؛ احتوى My CV.md على helpers قديمة ودوال غير موجودة مثل bulk وuploadBase64، وتعليمات تطلب تعديل content.js، وإلزام تمرير السجل الكامل في كل مرة.

أُزيلت الإجراءات الفنية القديمة من ملف السيرة مع حفظ قسم الحقائق وتفضيلات الحساب والإرسال والبريد. انتقلت قيود تنسيق الوكلاء إلى دليل التقديم. أصبح [عقد الوكيل](agent-contract.md) المرجع الوحيد للإجراءات الفنية، وأصبحت بقية الملفات تشير إليه. يُقرأ من سجل الخبرات ما يخص المنصة، وتضاف دروس جديدة ذات سبب واختبار بدل نسخ التاريخ في كل مهمة.

فُحص حفظ أقسام الحقائق والتفضيلات أثناء النقل؛ توجد شهادة hash دون نسخ قيمها في `scratch/cv-autofill-second-review/document-preservation.json`.

## ما يستحق التطوير لاحقًا

1. **مجموعة قبول واقعية للبوابات:** حالات ذات توقعات مؤكدة من Oracle وWorkday وGreenhouse وغيرها، مع قياس نسبة الحقول المتحقق منها والتدخلات المطلوبة والوقت والتراجع. جمع HTML وحده لا يصنع اختبارًا سلوكيًا تلقائيًا.
2. **تصنيف معاني أكثر حساسية للسياق:** ترتيب الأدلة وكشف التعارض بين القسم الدراسي والقسم المطلوب للتدريب، وبين تواريخ العمل والتدريب. ترقية قاعدة إلى العموم تحتاج أكثر من نجاح محلي واحد.
3. **مسار تفاعل متصفح موثوق:** دمج أوضح مع الوكيل للمكونات المغلقة أو التي ترفض الأحداث المصطنعة، بدل افتراض أن DOM driver سيغطيها.
4. **تحديث المحرك داخل الصفحة دون refresh:** مفيد عند تصحيح حقل والنموذج يحتوي بيانات؛ يحتاج إدارة دورة حياة وعزل صلاحيات واختبارات مستقلة. السلوك الحالي يؤجل التحديث لحفظ البيانات.
5. **إصدارات للقواعد وتجارب تراجع:** مقارنة جودة القاعدة قبل الترقية وبعدها، وإتاحة رجوع إذا زادت الأخطاء. لا يلزم إدخال نموذج لغوي قبل توفر هذه المقاييس والحالات.

هذه دفعة مكتملة ذات أدلة قابلة للإعادة، وليست ادعاء الوصول إلى أقصى تغطية ممكنة. تتوقف الإضافات الجديدة عندما لا ترتبط بحالة واقعية أو تحسن قابل للقياس، ثم تستأنف عند ظهور دليل جديد.
