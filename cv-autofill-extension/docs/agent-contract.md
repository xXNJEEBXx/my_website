# عقد تشغيل الإضافة والتحسن المستمر

هذا هو المرجع الوحيد للإجراءات الفنية الحالية. دليل التقديم ينظم عمل الشركات والتراكر، وagent-learnings سجل خبرات تاريخية؛ لا تُنسخ خطوات API بين هذه الملفات.

## قبل التشغيل

1. استخدم الحقائق والمرفقات الفعلية للمستخدم. لا تخمّن إجابة شخصية أو تختلق ملفًا. تعديل قواعد التعرف لا يغيّر data.js.
   إذا تعارضت نسخة بيانات الإضافة مع أحدث سيرة مؤكدة، سجّل التعارض ولا تملأ قيمة متنازعًا عليها أو تغيّر حقيقة شخصية بالتخمين.
2. راجع درس المنصة المعنية فقط من سجل الخبرات. لا تُحمّل السجل الكامل في كل عملية.
3. واجهة الصفحة العامة غير متزامنة: `await window.__CV_AGENT.inspect()` ثم plan/fill. __CV_APP داخل ISOLATED. فعّل جلسة التعبئة من لوحة الإضافة أو popup؛ لا تكرر طلبًا مرفوضًا بلا معالجة سببه.
4. لا تُعدّل DOM مباشرة لتجاوز الأداة. إذا احتاج الموقع تفاعل متصفح أصلي بسبب isTrusted أو مكوّن مغلق، استخدم تفاعل الوكيل المأذون، ثم أعد فحص الحالة وسجّل الحد بدل إعلان نجاح غير متحقق.

## أثناء التشغيل

الترتيب: قاعدة اعتمدها المستخدم ← قاعدة المنصة الحالية ← ربط موثوق تعلّمته الأداة ← metadata القياسية مثل autocomplete ← أنماط عامة ← حالة تحتاج مراجعة.

التخطيط لا يستهلك الروابط ولا ينقر النموذج. راجع الإجابات، ونفّذ عبر fill، واقرأ verifiedFields وfailedActions وblockedActions وcancelled. وجود قيمة في DOM لا يثبت قبول خادم التوظيف لها.

إذا ظهر حقل ناقص:

- **قيمة معروفة في السيرة:** أصلح معنى الحقل أو تنسيقه أو driver. يفضّل ربط fieldKey بالقيمة الحالية بدل حفظ النص الشخصي.
- **تفسير اعتمده المستخدم:** داخل السياق الموثوق استخدم `await __CV_AGENT.learn(uniqueSelector, confirmedAnswer)`، أو مرر `{ fieldKey, profileKey }` كوسيط ثالث لربط معنوي صريح. التعلم لا يشغّل التعبئة كأثر جانبي.
- **سؤال شخصي غير معروف أو معنى منفي/متعارض:** اتركه للمراجعة واطلب المعلومة الناقصة عند الحاجة. لا تجعل الحل «نعم للجميع» أو خفض عتبة المطابقة للجميع.
- **مكوّن لا يستجيب:** حدّد نوعه وبنيته ونتيجة الحدث، ثم حسّن driver العام إن أمكن؛ استخدم adapter عندما يكون الفرق خاصًا بالمنصة.

الأولوية للقواعد المعتمدة صراحةً. الربط التلقائي يأتي من نجاح قاعدة منصة موثوقة، ويخزن مفتاح السيرة لا نص الإجابة. القواعد المتزامنة تُكتب في طابور عامل الخلفية حتى لا تمسح بعضها. لا يُتعلم password/OTP، ولا تصبح الإجابات غير المعروفة قواعد تلقائية.

## ما يحدث تلقائيًا بعد كل تشغيل

- آخر 100 تشغيل تُسجّل داخل الإضافة: العدادات وأكواد المشاكل وتلميحات الفجوات المنظفة، دون قيم الحقول أو PDF.
- روابط الحقول الموثوقة تُحفظ للاستفادة منها إذا تغيّرت معرّفات الواجهة مع بقاء السؤال نفسه.
- عند تشغيل وضع التطوير، تُلتقط عينات HTML منظفة للنماذج الجديدة، وتُحفظ محليًا مع منع التكرار. خارج وضع التطوير لا تُرسل العينات إلى خادم.
- الوكيل يقرأ `await __CV_AGENT.improvementReport()` من السياق الموثوق عند تقييم التحسن. نجاح نموذج واحد لا يثبت دعم كل منصة.

## إغلاق حلقة التحسن

1. احتفظ بعينة أو سيناريو يعيد إنتاج الفجوة.
2. أضف اختبارًا للسلوك المطلوب يستعمل كود الإنتاج، وأثبت الخطأ قبل الإصلاح عندما يكون ذلك عمليًا.
3. أصلح أصغر طبقة مسؤولة: معنى/تنسيق/driver/adapter.
4. شغّل `node test-suite/run-tests.js`، واختبارات Chrome عند تغيير سلوك DOM أو التخزين أو الخلفية: `node test-suite/browser-tests.cjs`.
5. تحقق من اختفاء الفجوة في الحالة الأصلية وعدم تراجع الحالات السابقة. لا تغيّر الاختبار ليقبل الإجابة الخاطئة.
6. أضف درسًا واحدًا موجزًا إلى agent-learnings عند وجود معلومة جديدة: السبب، الحل، الاختبار، وحدود التعميم. لا تنسخ الوثائق أو تعيد الدرس نفسه مع كل شركة.

الإضافة تجمع الأدلة وتتعلم الربط؛ الوكيل يكتب تحسينات الكود ويختبرها. لا تدّعي أن runtime يكتب JavaScript جديدًا بنفسه.

## التحديث التلقائي

شغّل `npm --prefix cv-autofill-extension run dev`. ينشئ الخادم إعداد تطوير محليًا محميًا ومُستبعدًا من Git. بعد تحميل إصدار الإضافة الحالي، اضغط فحص لتتصل بوضع التطوير.

تُبنى المصادر وتُفحص صياغتها قبل نشر إشارة التحديث. يحتفظ الخادم برقم المراجعة، فلا تضيع الإشارة إذا أعيد تشغيل العامل. العامل يعيد الاتصال عبر alarms، ويحدث الإضافة والتبويبات المرتبطة بالنماذج الخالية فقط. أثناء تنفيذ أو وجود بيانات غير مرسلة يبقى التحديث معلقًا ويظهر تنبيه؛ لا يُحدّث التبويب النشط لمجرد أنه نشط. إيقاف خادم التطوير يعطل هذا المسار.

بعد تغيير كود الخادم نفسه أعد تشغيل أمر dev. إعادة تحميل الإضافة لأول مرة بعد تغيير manifest تبقى خطوة Chrome عادية. تفاصيل إيقاف العامل مع MV3 موثقة في [Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).

## حدود الادعاء والتوقف

الهدف توسيع التغطية مع كل حالة جديدة. لا يمكن إثبات «كل موقع وكل ظرف» بمجموعة اختبارات محدودة؛ توجد صفحات محظورة على الإضافات ومكونات مغلقة وأحداث موثوقة وتحقق بشري. اقرأ [صلاحيات الحقن](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) قبل اقتراح حل يحتاج صلاحية جديدة.

تكتمل دفعة التحسين عند معالجة الأخطاء المعروفة، ونجاح الاختبارات ذات الصلة، ووجود دليل قابل للإعادة، وتوثيق الحدود. أوقف التغيير عندما تكون الخطوة التالية تعقيدًا بلا حالة واقعية أو تحسن قابل للقياس. تبقى شاشة تأكيد التقديم الفعلية ولقطتها شرط تسجيل التقديم في التراكر؛ الاختبارات المحلية ليست تقديمًا حيًا.
